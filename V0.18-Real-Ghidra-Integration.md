# V0.18 — Real Ghidra 12.2 integration gate

## Objective

Move the V0.17 Ghidra frontend from synthetic JSON contract tests to an automated test that starts the official Ghidra Headless Analyzer, compiles and runs the Java exporter, consumes Ghidra-generated P-code, lowers the supported subset, and verifies the reconstructed function against the original ELF function.

## API correction found before runtime testing

Inspection of the official Ghidra_12.2_build source showed that Language.getRegister accepts:

    getRegister(AddressSpace addrspc, long offset, int size)

The V0.17 exporter had called it with (Address, int), which is not the Ghidra 12.2 API signature. The exporter now passes the varnode's address space, offset, and size. This is a source-level API correction; the Java script still needs to compile and execute in the real Ghidra runtime.

## New real-integration workflow

The .github/workflows/ghidra-12-2-integration.yml workflow:

1. Uses Java 25 and Python 3.13.
2. Downloads the official Ghidra 12.2 release archive.
3. Verifies the archive SHA-256 against the release asset digest before extraction.
4. Runs the existing Python regression suite.
5. Builds a tiny x86-64 ELF shared-library fixture with DWARF parameter metadata and deliberately constrained machine code.
6. Runs analyzeHeadless with ChronoExport.java.
7. Validates the actual JSON export and lowers the actual P-code.
8. Compiles the candidate, checks equivalence with the existing bit-vector model, and replays boundary plus deterministic random inputs.
9. Uploads the raw P-code export, decompiler C output, smoke report, and fixture binary even when the integration job fails.

The release is pinned to Ghidra_12.2_build, archive ghidra_12.2_PUBLIC_20261016.zip, SHA-256:

    2c2cd776db3c1f6a097ba418922378ac3649cadd5e844a6f5f088ae628a7be67

Ghidra 12.2's official Getting Started guide specifies a 64-bit Java 25 JDK requirement.

## Controlled native fixture

The tests/fixtures/ghidra_mul_add.c fixture uses a DWARF-described uint32_t function and inline assembly to keep its body to:

- imul $5, %edi, %eax
- add $3, %eax
- ret

This avoids compiler-dependent instruction selection and keeps the test aligned with the current P-code lowering subset. The source is compiled as a trusted ELF shared object; its exported symbol is replayed natively.

## Smoke runner

The scripts/ghidra_smoke.py runner performs one real export and writes:
- function.json — raw Ghidra schema-v1 P-code and function metadata;
- decompiled.c — Ghidra's C decompilation;
- ghidra-export-result.json — export and validation summary;
- ghidra-smoke-report.json — lowering and verification outcome.

The smoke test only passes on DIRECT_VERIFIED with SMT UNSAT. Unsupported P-code, export errors, solver UNKNOWN, and replay mismatches remain failures; they are not converted into success.

## Acceptance status

**Real Ghidra acceptance is pending.** The development container has Java 21 and no Ghidra installation. The Java exporter has therefore not yet been compiled or executed by Ghidra 12.2, and no real Ghidra-generated P-code result is claimed here.

The GitHub Actions run is the next evidence gate. If it fails, use the uploaded logs and actual function.json/decompiled.c artifacts to repair the specific API, export, ABI, or P-code mismatch. Do not broaden the lowering subset until the actual export shape is understood.

## Next engineering steps after the first real run

1. Fix any Ghidra 12.2 runtime or schema mismatch found by CI.
2. Preserve the real P-code export as a versioned regression fixture.
3. Add a second real fixture with a simple conditional branch.
4. Only then extend the lowering path to multi-block CFGs, conditional branches, and MULTIEQUAL/phi nodes.
5. Keep loops, memory, calls, and unknown operations fail-closed until separately modeled and tested.
